# CNN-00 CP3-A — Scientific Requirements and Architecture Evidence Matrix

**Scope:** CP3-A only. This is a source-linked requirements/evidence investigation, not an architecture selection, option dossier, implementation plan, teardown contract, or scientific evaluation. No architecture is ranked or selected. CP3-B, CP3-C, reconstruction, and CNN-01 remain outside scope.

**Source baseline:** `404d76112a9d53282b3f55698b4decb705a5601c` (`main` at claim and report preparation). **Expected changed path:** this report only. No tests, probes, training, benchmarks, or experiments were run for CP3-A.

**Authorization and method:** the thesis author authorized CP3-A only in [issue #25 comment 6814413872](https://github.com/midhunpradeep/town_model/issues/25#issuecomment-6814413872), with methodology in [comment 6814361581](https://github.com/midhunpradeep/town_model/issues/25#issuecomment-6814361581). This report records current interfaces and accepted evidence, crosswalks those to the relevant scientific and retained software requirements, and identifies capability gaps, assumptions, dependencies, and approval gates. It does not choose a design or create new scientific requirements.

### 1.2 Evidence categories

The matrix uses these categories explicitly; one category does not promote a statement into another:

| Category | Meaning in this report |
|---|---|
| **Author-approved scientific requirement** | A1 F0–F10 or the separately recorded F11/F12 author-reported decisions, with the recorded scope and provenance limits. |
| **Author-confirmed interface specification** | R2/ADR interface behavior explicitly confirmed by the author; it does not authorize implementation. |
| **Retained software/interface contract** | A type, tensor, identity, or fail-closed boundary retained and accepted in the current classifier-free system. Not automatically a scientific axiom. |
| **Source-observed behavior** | Behavior visible in the exact current source revision. Static inspection establishes code structure, not runtime performance. |
| **Empirically observed — named fixture** | Only the result actually established by an independently accepted CP2 synthetic CPU probe at its fixed fixture, tolerance, and environment. |
| **Historically reported** | A result or interface from a prior implementation/review at its own revision; it is not current execution evidence or renewed approval. |
| **Mathematical implication (conditional)** | A consequence of the stated operation under explicit assumptions; not a measured outcome or additional approval. |
| **Hypothesis / unresolved author-owned** | A question or possible consequence not settled by the approved sources or evidence. No answer is inferred here. |

## 4. Confirmed conflicts, missing functionality, and untested assumptions

### 4.1 Confirmed authority conflicts

**No direct contradiction among the reviewed A1, F11, F12, ADR-0001/0002, R2 confirmed interface decisions, T5 operational boundary, and accepted BOX/TOWN contracts was identified.** The distinctions are chiefly between requirements for future scientific stages and the intentionally smaller current classifier-free foundation.

### 4.2 Confirmed requirement-to-capability gaps (not architecture verdicts)

1. **Unbounded image-point path:** A1 F2.7 plus ADR-0002 specify bounded and unbounded image runs, while current heads expose only bounded tanh. This is a confirmed missing capability relative to full two-domain image integration, not a conflict with the retained bounded path.
2. **Detector stages:** F9.1 requires three detector-dependent stages. Current source has no detector, selected detector checkpoint, predicted-ROI provider, matcher, or stage trainer. The existing ImageNet/FPN GT-ROI path is not detector-pretrained Stage 2. This is missing future functionality; Phase 3 was explicitly pre-detector.
3. **Domain/class identity in CNN run state:** ADR-0001/0002 require class/domain/activation identity at the appropriate classifier/run/checkpoint boundary. Current point results and historical image config do not carry unbounded domain/activation identity, and model-dependent checkpoint operations are unavailable. This is missing future integration, not a live checkpoint corruption finding.
4. **Sample/feature row association:** feature tensors do not carry sample IDs; sample IDs are supplied separately to the point model and only batch length is checked. This is a source-observed limitation and caller precondition, not a reproduced data misalignment.
5. **Predicted detection identity:** current `ROIIdentity` has an occurrence ID and optional detector category/confidence; it does not define how one-to-one prediction identity, missed annotations, duplicates, unmatched detections, or annotation reconciliation work. No active predicted-ROI path exists. This is unresolved Stage-3 functionality, not an observed bug.
6. **BOX/TOWN integration:** accepted BOX/TOWN surfaces are point-only bounded evaluators. BOX-04 has an exact class-bound typed result; TOWN-02 has raw per-point house/town membership functions. Neither is an image adapter or a complete common CNN classifier interface. Compatibility is not demonstrated; no current integration was required or performed.

### 4.3 Historical settings and untested assumptions (not confirmed active conflicts)

- Historical image-training defaults differ from F12.12 defaults. Because current run/training operations fail closed and the old config is explicitly metadata, these differences are **not** an active runtime contradiction. They become a required reconciliation only if a future authorized trainer reuses that schema.
- CP1 source inspection and tests establish structural contracts/coverage descriptions, not a newly run regression result in this CP3-A task. CP2 is synthetic CPU evidence only. No real-image feature quality, detector behavior, CUDA path, optimizer behavior, scientific learning, held-out evaluation, or generalization claim is established here.
- Spatial averaging is non-injective on arbitrary ROI activation maps. Whether that loss affects relevant visual distinctions is untested; no performance or architecture claim follows.
- The FPN/global ROI and ROI-coordinate behavior are source-supported and have bounded synthetic CP2 evidence. Generalization to arbitrary image sizes, detector outputs, data distributions, or stage-specific weights is not established by those probes.
- A1 records dashboard inspection requirements in its project/infrastructure context, outside the numbered F0–F12 mathematical decisions. The CP3 methodology also calls out preserving inspection needs and future phase controls. These requirements do not authorize restoring old model-dependent execution: the T5 fail-closed boundary remains controlling until separately approved and accepted.

## 5. Architectural dependency map (descriptive, not a design recommendation)

```text
prepared dataset / canonical class manifest / sample & occurrence IDs
          │                         │
          │                         └── targets + known masks (supervision only)
          ▼
ImageBatch + original-pixel boxes + ImageGeometry
          │
          ├── GT ROI provider (current) / predicted provider (not implemented)
          ▼
MobileNetV3-Large + FPN (current shared visual state)
          ├── component ROIAlign → spatial mean + four coordinates → [B,K,260]
          │       └── component point projection → [B,K,d] + occurrence-valid mask
          └── full-original-image ROIAlign → [B,256,7,7]
                  └── global point projection → [B,d]
component points + valid mask ── DeepSets sum/rho ── composed pizza point
                    global point + composed point ── hybrid fusion
                                  │
                                  ▼
                     ImagePointResult (points/IDs only)
                                  │
                  future, separately approved adapter boundary
                    ├── class binding / domain identity
                    ├── BOX/TOWN point evaluator(s)
                    ├── F8 objective + mask/reducer path
                    └── stage-specific trainer/checkpoint lineage
                                  │
                  versioned inspection + dashboard presentation
```

Dependency implications:

- Encoder initialization, FPN state, preprocessing, ROI coordinates, and ROI source determine visual-cache producer identity and any future Stage-1→Stage-2 checkpoint lineage.
- Component extraction determines the `[B,K,260]` feature contract and therefore component projection input compatibility. Global extraction determines the `[B,256,7,7]` contract and global projection input compatibility. These are separate paths after shared FPN maps.
- Output dimension `d` and domain/activation affect component/global/composition/fusion outputs, point-to-classifier inputs, run identity, and checkpoint semantics. Same-shaped weights do not remove semantic domain differences.
- Component validity/padding, component occurrence identity, sample identity, and ontology known masks have different meanings and must stay separately traceable. Composition depends on occurrence validity; F8 objectives depend on known-label masks.
- ROI source and prediction-to-entity mapping depend on scientific stage. Stage 2 and Stage 3 require different detector lineage, trainability/state, and ROI provenance. No Stage-3 identity or matching behavior is supplied by the current provider abstraction.
- Class-column identity and point-domain identity belong at the future classifier/run/checkpoint boundary. BOX-04 supplies a bounded BOX binding interface; current TOWN pure functions and CNN point transport do not form a common adapter.
- Snapshot/read-only dashboard behavior depends on versioned producer identities and explicit stored axes. Current T5 policy prevents dashboard presentation from reconstructing retired classifier semantics or publishing new classifier outputs.

9. **Cache/checkpoint versioning:** how future domain, activation, predicted ROI, detector, class-binding, and stage identities affect cache or checkpoint schemas. Current visual cache is frozen/GT-only and current historical model operations are unavailable.
10. **Scientific interpretation:** F11 requires separating realizability, numerical feasibility, optimization, and generalization and preserving evidence provenance; final operational protocols and claim criteria remain open where A1/F11 state them as open.
